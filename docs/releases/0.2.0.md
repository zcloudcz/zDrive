## Changes

- New zDrive icon derived from the zCloud logo: a white cloud/infinity symbol,
  orange sync arrow and drive tray on charcoal. The source PNG is
  `src/client/zdrive_app/assets/branding/zdrive-icon.png`; platform launcher
  assets include the Windows ICO.
- Windows displays **zDrive** while retaining `ProductName=zdrive_app` so
  `path_provider` continues to locate existing application data.
- A small online Windows x64 installer downloads a versioned ZIP over HTTPS
  and verifies its embedded SHA-256 digest before extraction. Packaging rejects
  a setup executable larger than 5 MB. A WinForms progress window guides setup.
  Installation uses the current user's profile and preserves application data
  on uninstall.
- File download, version restore, sync and recovery improvements are described
  in [MVP completion notes](../mvp-completion.md), including their limitations.

The installer is unsigned unless signed separately. Its IExpress bootstrapper
uses the standard setup icon; the installed app and shortcuts use the zDrive
icon. PhotoService and NotificationService are not deployed by this release.

## Package and publish

Run from the repository root on Windows after the production-configured Flutter
release build. See [Windows packaging](../../packaging/windows/README.md) for
installation paths and behavior.

```powershell
./scripts/Package-Windows.ps1 `
  -ReleaseDirectory ./src/client/zdrive_app/build/windows/x64/runner/Release `
  -RuntimeDirectory 'C:/Program Files/Microsoft Visual Studio/18/Community/VC/Redist/MSVC/14.51.36231/x64/Microsoft.VC145.CRT' `
  -Version 0.2.0 `
  -PayloadUrl 'https://drive.zcloud.cz/downloads/zDrive-0.2.0-windows-x64.zip'
```

Keep the setup and ZIP from the same packaging invocation. The ZIP contains an
`app/` directory plus installation scripts. Never replace a published version's
ZIP with different bytes, because the setup pins its digest.

After review and validation, upload these generated assets from
`build/windows-installer` to release `v0.2.0` in private repository
`zcloudcz/zDrive`:

- `zDrive-0.2.0-Setup.exe`
- `zDrive-0.2.0-windows-x64.zip`

The locally packaged setup is **196,608 bytes**; the payload ZIP is
**15,124,438 bytes**, with SHA-256:

```text
C132AB366EFD6D5142028C147927EA2198334825A871B5829D39DDEC313FE01E
```

Repackaging changes the artifact evidence; record new sizes and hashes if rebuilt.

The [web deployment workflow](../../.github/workflows/deploy-web.yml) reads the
version from `pubspec.yaml`, fetches those named assets using its GitHub token
and publishes them with the web client. It also retains complete published
Windows releases so older installers can still download their pinned payloads.
Public download locations are planned:

- [Windows setup](https://drive.zcloud.cz/downloads/zDrive-0.2.0-Setup.exe)
- [Windows payload](https://drive.zcloud.cz/downloads/zDrive-0.2.0-windows-x64.zip)

These URLs are not yet verified as published. Private GitHub download URLs
cannot serve as the installer's public payload URL.

## Production rollout

Use authenticated Azure CLI and GitHub access. Existing Azure apps are
`zdrive-gateway`, `zdrive-auth`, `zdrive-file`, `zdrive-storage` and `zdrive-sync`
in resource group `invoiceapi`, on shared plan `asp-fakvio-b1`. This rollout
creates no new billable resources.

SyncService now uses direct ZIP deployment like the other services, replacing
its remote package setting. The previous setting is protected with Windows DPAPI
in ignored `TestResults`; do not publish its decrypted contents.

1. Authorization, CI and Hydra review are complete for the PR head above.
   Preserve the backup ZIPs and their manifest for rollback.
2. All five backend deployments are complete. For repeat deployment, the command
   for the prepared framework-dependent Linux ZIPs is below. Set `$service` to
   `storage`, `file`, `sync`, `auth` and `gateway` in turn, checking each service
   before continuing:

   ```powershell
   az webapp deploy --resource-group invoiceapi --name "zdrive-$service" `
     --src-path "TestResults/production-publish/$service.zip" `
     --type zip --clean true --restart true --timeout 600000
   ```

3. Health checks and the isolated production API smoke passed. After any repeat
   deployment, verify `/health/live` and `/health/ready` return 200 for all five
   apps and exercise authenticated upload, download and restore through the
   gateway. Confirm metadata supplies the committed manifest hash and
   `GET /api/v1/storage/download/{fileId}/manifest?manifestHash={hash}` confirms
   that same hash.
4. Publish the versioned release assets, then merge to `master`. Changes to
   the client or deployment workflow trigger Pages automatically, so the
   backend must be ready and release assets available before merging.
5. After Pages succeeds, check both public downloads without authentication,
   compare their SHA-256 hashes with the local artifacts, and exercise setup
   from the public URL in a disposable Windows account or VM. Verify login,
   upload, download, sync, trash recovery and version restore in the released
   clients. Record deployment IDs and results before marking this release live.

**Deploy the backend before clients.** New clients require immutable manifest
hash confirmation. Publishing them against the old StorageService can interrupt
downloads even when basic health checks pass.

## Rollback

Before client publication, redeploy the affected service's backup using the
same command above, substituting
`TestResults/production-backup-20260916/zdrive-$service.zip` as the source.
Verify the backup hash against `manifest.json`, then repeat health and
authenticated file checks. These ZIPs back up application files, not database
contents or Azure configuration.

For SyncService, direct ZIP rollback restores application binaries under the new
deployment configuration. Restoring the former remote-package configuration is
a separate operation using its DPAPI-protected backup.

After client publication, coordinate rollback with the release owner: installed
0.2.0 clients still require the new StorageService contract. Reverting the web
client does not downgrade desktop installations. Keep a compatible backend
available or prepare a compatible client recovery before reverting that
contract. Pause further publication if verification fails and record the
affected deployment and failed check.
